# 03 — Logical model

Third step of the design process. Maps the [conceptual model](02-conceptual-model.md) to relational
structures: tables, columns, primary keys and foreign keys. Still independent of PostgreSQL-specific
details (exact types, indexes), which belong to the physical model.

## Mapping rules

| Conceptual | Logical |
|---|---|
| Entity | Table |
| Weak entity (exercise entry, set) | Table with a foreign key to its owner and a unique order within it (see "Primary keys") |
| Simple attribute | Column |
| 1:N relationship | Foreign key on the N side |
| 1:N relationship with optional owner (user creates exercise / alias) | Nullable foreign key: empty means "system" |
| N:N relationship with attribute (exercise works muscle group, role) | Association table holding both foreign keys and the attribute |

## Primary keys

**Every table uses an artificial primary key: a UUID version 7**, for the same reasons as in the Planner:
natural keys change, sequential integers leak information and collide across tools, and version 7 UUIDs
are unique everywhere, can be generated by the client before saving, and arrive in index order.

- **Weak entities too.** Entries and sets would naturally be identified by their owner plus their order, but
  the order changes whenever the user reorders them, and a primary key must not change. Each gets a UUID, and
  `(owner, order)` becomes a unique constraint.

Two deliberate exceptions:

- **`muscle_groups` uses a text code as its key** (`chest`, `triceps`…). It is a fixed catalog that ships
  with the system and never changes, and a readable code is what clients and AI agents actually send
  (`"muscleGroup": "chest"` instead of a UUID they would have to look up first). Same idea as the property keys
  of the Planner's catalog.
- **`exercise_muscle_groups` uses a composite key** `(exercise_id, muscle_group_code)`. It is a pure association
  table: the pair is the identity, and it also enforces "a muscle group appears at most once per exercise".

Natural keys remain as **unique constraints** (candidate keys):

- `users.email` is unique.
- `(workout_exercises.workout_id, workout_exercises.sort_order)` is unique.
- `(workout_sets.workout_exercise_id, workout_sets.sort_order)` is unique.
- `(body_weights.user_id, body_weights.measured_on)` is unique.
- `(exercises.user_id, exercises.name)` is unique, with the empty `user_id` (system) counting as one scope.
- `(exercise_aliases.user_id, exercise_aliases.term)` is unique, same scoping. See "Search terms".

## Naming

Table and column names are English, `snake_case`, and tables are plural, as in the Planner.

- **`workout_sets`, not `sets`:** `SET` is an SQL keyword, and the prefix keeps the table next to
  `workout_exercises` in listings.
- **`workout_exercises`** is the conceptual *exercise entry*: an exercise as performed in a given workout.
- **Columns with a unit carry it in the name** (`load_kg`, `distance_m`, `duration_sec`), so no client or agent
  has to guess whether a duration is in seconds or minutes.
- **Booleans start with `is_`** (`is_unilateral`, `is_failed`).

## Set measurements

Every set lives in **one table with one nullable column per measurement**, and the exercise's measurement
type decides which columns are filled:

| Measurement type | `reps` | `load_kg` | `assistance_kg` | `duration_sec` | `distance_m` |
|---|---|---|---|---|---|
| `weight_reps` | required | required | — | — | — |
| `bodyweight` | required | optional | optional | — | — |
| `time` | — | — | — | required | — |
| `distance_time` | — | — | — | required | required |

`—` means the column must stay empty. In `bodyweight`, `load_kg` and `assistance_kg` are never filled together.

- **Load and assistance are two columns, not one signed number.** A negative load meaning "assisted" is the
  kind of convention a client or an LLM gets wrong silently. With two columns, each value is non-negative
  and means exactly what its name says. The real load is still a simple query:
  `body weight + load_kg − assistance_kg`.
- **Rejected — one table per measurement type** (`weight_sets`, `time_sets`…): reading a workout would join
  four tables, and an entry's sets would be split by type for no gain. The four types share almost every
  column (order, type, failed, side).
- **Rejected — measurements in a JSON column** (as the Planner's properties): the set's fields are few, fixed
  and numeric, and every analysis (volume, records, pace) aggregates them. Regular columns keep their types,
  can be checked by the database, and are trivial to sum.
- **The rule crosses tables:** the measurement type lives in `exercises`, the values in `workout_sets`. The API
  validates every set against its exercise's type; whether the database also enforces it (trigger, or copying
  the type into the entry) is decided in the physical model.
- **Consequence — the measurement type of an exercise cannot change once any entry uses it,** or its existing
  sets would stop matching. New rule, derived from the above; added to the constraints below.

## Search terms

Constraint 4 is enforced by **uniqueness within each scope plus a fixed search precedence**, not by
uniqueness across scopes:

- **Within a scope** (the system, or one user), names are unique in `exercises` and aliases are unique in
  `exercise_aliases` — two plain unique constraints, where an empty `user_id` counts as one scope.
- **A search resolves in a fixed order** and returns the first match: the user's exercise names, the user's
  aliases, system exercise names, system aliases. Two scopes may share a term; the order decides, so the
  answer is always a single exercise.
- **A user's exercise cannot take the name of a system exercise** (checked by the API), so lists never show two
  exercises with the same name. Aliases are free to shadow system terms: that is the user saying what a word
  means to them.
- **The API also refuses** a new name or alias that clashes with another term of the same scope in the other
  table (a user alias equal to one of their exercise names). The precedence keeps searches deterministic even
  if such a clash slipped through.

Rejected:

- **Uniqueness across scopes** (a user's term may not repeat any system term): it cannot be a plain unique
  constraint, needs a trigger with locking, and makes adding a system alias in a later migration fail for
  every user who already used that word.
- **Only the API checks, nothing in the database:** two concurrent requests could both pass the check.
- **One table holding every search term** (names and aliases together): the exercise name would be stored
  twice, and it would still not solve the clash between scopes.

## Tables

```
users
  id                  PK
  name
  email               UNIQUE
  created_at
  updated_at

muscle_groups                       (fixed catalog, created by a migration)
  code                PK            (chest, back, shoulders, biceps, triceps, forearms,
                                     quadriceps, hamstrings, glutes, calves, abs)
  name                              (display name)

exercises
  id                  PK
  user_id             FK → users.id   (empty for system exercises)
  name
  measurement_type                  (weight_reps | bodyweight | time | distance_time)
  is_unilateral
  created_at
  updated_at

exercise_muscle_groups
  exercise_id         PK, FK → exercises.id
  muscle_group_code   PK, FK → muscle_groups.code
  role                              (primary | secondary)

exercise_aliases
  id                  PK
  exercise_id         FK → exercises.id
  user_id             FK → users.id   (empty for system aliases)
  term
  created_at
  updated_at

workouts
  id                  PK
  user_id             FK → users.id
  started_at                        (date and time)
  duration_sec                      (optional)
  note                              (optional)
  created_at
  updated_at

workout_exercises
  id                  PK
  workout_id          FK → workouts.id
  exercise_id         FK → exercises.id
  sort_order
  UNIQUE (workout_id, sort_order)

workout_sets
  id                  PK
  workout_exercise_id FK → workout_exercises.id
  sort_order
  set_type                          (warmup | working)
  is_failed
  reps                              (optional, see "Set measurements")
  load_kg                           (optional)
  assistance_kg                     (optional)
  duration_sec                      (optional)
  distance_m                        (optional)
  side                              (optional; left | right; unilateral exercises only)
  UNIQUE (workout_exercise_id, sort_order)

body_weights
  id                  PK
  user_id             FK → users.id
  measured_on                       (date)
  weight_kg
  created_at
  updated_at
  UNIQUE (user_id, measured_on)
```

- **No `created_at`/`updated_at` on entries and sets:** as in the conceptual model, they are part of their
  workout. Any change to them updates `workouts.updated_at`, which is what "what changed since…" queries read.
- **No `user_id` on entries and sets:** the owner is reached through the workout. Copying it down would be a
  redundancy with nothing to gain at this size.
- **Value lists** (`measurement_type`, `role`, `set_type`, `side`) are fixed by the system. Whether they become
  PostgreSQL enums, text with a check, or lookup tables is decided in the physical model.

## Constraints

Carried over from the conceptual model, now in terms of tables:

1. **Measurements follow the type:** see "Set measurements". All numeric values are non-negative
   (`reps` may be 0 in a failed set: the first repetition was attempted and not completed);
   `body_weights.weight_kg` is positive.
2. **Side only on unilateral exercises:** `workout_sets.side` may be filled only if the entry's exercise has
   `is_unilateral`.
3. **Visible exercises only:**
   - `workout_exercises.exercise_id` points to a system exercise or to one whose `user_id` equals the
     workout's `user_id`;
   - a user's alias points to a system exercise or to one of their own;
   - a system alias (`user_id` empty) points only to a system exercise.
4. **One term, one exercise, by scope and precedence:** see "Search terms".
5. **System exercises list their muscle groups:** a system exercise has at least one row in
   `exercise_muscle_groups` with role `primary`, unless its `measurement_type` is `distance_time` (cardio has
   no muscle groups, so it never inflates per-muscle analyses).
6. **Measurement type is frozen once used:** `exercises.measurement_type` cannot change while any
   `workout_exercises` row points to the exercise. *(New — derived from "Set measurements".)* Fixing a wrong
   type means creating a new exercise; an explicit "convert exercise" operation, migrating the sets where a
   conversion makes sense, may come later as an API operation without changing the model.
7. **An entry has at least one set:** a `workout_exercises` row without `workout_sets` is invalid. Enforced by
   the API, which creates and replaces an entry together with its sets.
8. **Deletes:**
   - `workouts` → deletes its `workout_exercises`, which delete their `workout_sets` (cascade);
   - `exercises` → blocked while referenced by `workout_exercises`; otherwise deletes its
     `exercise_aliases` and `exercise_muscle_groups` (cascade);
   - `muscle_groups` and system rows are only changed by migrations.

## Normalization

- **1NF — one value per cell.** Every column holds a single value; the measurements of a set are separate
  columns, not a list. No JSON columns.
- **2NF — depend on the whole key.** Every table but one has a single-column key. In
  `exercise_muscle_groups`, `role` depends on the pair (the same exercise has different roles for different
  muscle groups), so it complies.
- **3NF — depend on nothing but the key.** No transitive dependencies: the user of an entry or set is reached
  through the workout and not copied, and the measurement type stays in `exercises` instead of being repeated
  in each set.
- **Nullable columns in `workout_sets`** are not a normal-form violation: each column depends on the set's key.
  They are the price of keeping one table for four measurement types, discussed in "Set measurements".
